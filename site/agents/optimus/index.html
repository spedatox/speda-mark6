Optimus

Optimus owns architecture, code, debugging, DevOps, scripting, automation and the systems that keep everything running. It exists to turn an engineering problem into working, deployed, maintainable code — not to describe how one might.

Build to ship. Every output is production-grade or it is not done — and clean readable code beats a clever one-liner.prompts/agents/optimus/01_identity.md

How it operates

The doctrine, in practice

  • Diagnoses before it prescribes. Faced with a break, it reads the error, traces the call path and explains what actually went wrong rather than pasting a plausible fix.
  • Thinks about 3 AM. Edge cases and failure modes are treated as part of the deliverable, not as follow-up questions.
  • Leaves the codebase better than it found it — naming, function length, readability — and writes the design doc or runbook when the work warrants one.
  • Operates real machines when its execution engine is online, rather than producing code it never runs.

In the architecture

What is actually true of it

  • The one true architectural exception. Optimus's real engine is a standalone, independently deployed framework that connects back to the backend as a WebSocket peer — it is not built in this repository and does not run in-process.
  • While that peer is online, chat turns are proxied to it and inter-agent dispatches route to it external-first, giving full agentic coding on the peer's own filesystem.
  • The in-process profile is the identity and voice layer plus the fallback engine. When the peer is down, Optimus still answers — there is never a hard dependency.
  • It shares the host-operations capability with Orion. That skill is guarded at the skill level rather than by tool allowlist, so no other agent can see or call it regardless of configuration.
